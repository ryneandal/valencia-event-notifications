**Brisa: product opportunities to test**

21 October 2026. Proposal only; these priorities are not implementation, delivery, or pricing commitments.

Start with a two-week test of one promise: **Brisa helps a resident choose something worth doing tomorrow.** Improve the presentation of real results, measure whether people use them again, then test interest in an optional household membership. Coverage and repeat usefulness should decide the next investment.

**What the current product establishes**

This review used repository sources, without accessing live accounts or sending messages. Code observations and deployment records provide different kinds of evidence:

| Evidence | What it supports |
| --- | --- |
| [App.jsx](../cloudflare/pages/src/App.jsx), [profile.js](../cloudflare/pages/src/profile.js), and [onboarding.js](../cloudflare/pages/src/onboarding.js) | Seven onboarding steps start with email. New forms preselect a family audience, several preferences, and seasonal anchors. Users can choose 1–12 event types. The review names interests but summarizes positive and negative preferences as counts. |
| [DigestPreview.jsx](../cloudflare/pages/src/DigestPreview.jsx) | An authenticated account can request tomorrow's preview. Cards show event titles, source links, eligibility decisions, and numeric scores. Detailed per-type explanations already sit inside a disclosure. The default preview lists evaluations, including rejected candidates; it does not present the final ranked digest as plan cards with time and practical details. |
| [User management specification](user_management.md) and [Jev integration plan](jev-integration-plan.md) | Saved profiles and magic-link access support personalized previews. Jev checks event types; the other saved preferences continue through ranking. Only scores strictly above 0.6 cause type-based rejection; uncertainty keeps the fallback path available. A type match does not establish family suitability, accessibility, or a final recommendation. |
| [Release record](jev-deployment-2026-10-21.md) and task handoff | The record reports a successful authenticated production preview, active filtering, and disabled digest delivery pending its separate smoke test and sender readiness. The handoff identifies one cinema agenda item in the sample run. That sample cannot establish coverage across València, classification accuracy across all types, or demand. |

No retention, willingness-to-pay, attendance, or broad inventory evidence was available for this proposal. The working assumptions are that some residents make next-day decisions repeatedly, that the existing family-oriented choices suit an initial test cohort, and that convenience might justify payment. Each needs testing. All example copy below describes proposed behavior, not shipped behavior.

**Ranked UX improvements**

| Rank | Visible starting point | Proposed change and a useful check |
| --- | --- | --- |
| 1. Show a usable shortlist | The preview presents type evaluations, while an “eligible” event may still rank poorly on other saved preferences. | Lead with the actual ranked recommendations. Each card should show the date and known time, source, and available practical facts, followed by “View organizer details.” Keep reviewed-but-excluded events in an optional section. This requires the backend to expose the recommendation result; the browser must not infer it from eligibility. Check whether someone can choose a next action without interpreting a score. |
| 2. Give empty results an honest next step | The current messages are “No events found for tomorrow. Try again later” and “All evaluated events are irrelevant for your selected types.” | Separate an empty collection, no matches after filtering, and an incomplete fetch. State the date and last successful check when known. Offer preference editing or a later check; don't automatically broaden choices or restore rejected events. Test these states separately using the examples below. |
| 3. Reduce work before the first useful result | All seven steps precede a saved, authenticated preview, and family choices arrive preselected. | Prototype a shorter path through audience, area, and types, then account access and review. Make extra preferences and seasonal anchors optional refinements. Ask people to choose their audience; use any family preset only after they select it. Preserve existing saved choices and the authenticated preview boundary. A clearly labeled example digest can demonstrate the format before signup without pretending to be live results. Measure completion and misunderstood defaults. |
| 4. Make the review editable and readable | “4 positive signals” tells someone little about what they are saving; editing uses the step sequence. | Show the actual labels, such as “Daytime · Near public transit,” with an edit action for each section. Explain that “Usually avoid” influences ranking; it is not a guarantee about an event. Keep saving explicit and previews tied to saved choices. Check whether participants spot and correct one deliberately wrong preference. |
| 5. Keep explanations brief by default | Numeric irrelevance scores appear on every evaluated card, alongside the existing “Why this result?” disclosure. | Use one supported sentence beside the result, for example “Matches your cinema interest; your other choices help order the shortlist.” Move scores, model details, and the preview reference into the existing disclosure or support details. An uncertain check can say “The event type is unclear from this listing.” Never turn model percentages into a promise of enjoyment or verified suitability. Test whether readers distinguish a type match from a recommendation. |
| 6. Make the returning account about tomorrow | The account screen's primary action edits the profile; the preview action says “Preview tomorrow safely.” | Make “See tomorrow's plans” the primary action, with the actual local date beside the result. Keep profile editing and pause controls easy to find. Show whether results reflect the saved choices, and when they were checked. The no-email explanation remains useful supporting text; it need not dominate the action label. |
| 7. Let users choose the rhythm | The product promises one email and offers pause/resume, but the current UI has no delivery-day choice and production sending remains off. | State the actual service state in plain language, such as “Preview is available. Email delivery hasn't started yet.” Before any delivery pilot, obtain clear agreement to its days and frequency. Later test selected weekdays or a weekend edition, plus pause and unsubscribe in every edition. Useful retention means new plans on days people want them, not daily reminders to inspect an empty page. |

For an empty collection, proposed copy is: “We haven't found any listings for Thursday 22 October in the sources checked so far. Last checked at [actual time].” Offer “Check again” and “Edit my choices.” This avoids claiming that nothing is happening in the city. If a source failed, say the search is incomplete rather than presenting a completed empty result.

For a hypothetical all-filtered case: “We checked 4 listings for Thursday. None matched your selected event types.” Offer “Review my event types” and a collapsed “See the 4 checked listings.” Show that count only when every candidate has a completed rejection; an uncertain or unavailable check does not belong in that bucket. A mixed result should lead with the recommendations and keep uncertain/rejected assessments distinct below them. Reviewing an excluded item must not silently add it back to the digest.

**Value additions worth testing after the preview is useful**

| Order | Addition | Benefit and smallest test |
| --- | --- | --- |
| 1 | More dependable event coverage | Record source freshness and the number of usable, dated events across several days and selected types. Manually compare a small sample with organizer information. Choose the next source because it fills an observed gap, not because the source count looks impressive. The one-item sample makes this an open question, not proof that a particular category lacks demand. |
| 2 | Planning actions with sourced facts | A calendar entry, organizer booking link, and directions can turn discovery into a plan. Use confirmed times and locations; label missing information instead of inventing price, age range, or access details. Test a simple calendar export on a few complete listings before building a trip planner. |
| 3 | A useful planning horizon | Offer a prototype of “Tomorrow” versus “This weekend” or a seven-day view. Ask participants which fits actual decisions, then test a chosen-day roundup only if future-dated inventory supports it. A saved plan with an optional reminder can give people a reason to return without repeating the same listings each day. |
| 4 | A shared household shortlist | Let someone copy selected public event links or share an explicitly chosen list with their partner or friends. Start with a copy action; test whether it replaces the manual forwarding people otherwise do. A share should contain only the chosen events, never the person's profile, email, private scores, or account link. |

**Plausible ways to pay for the service**

These are business hypotheses, not evidence of buyer demand. No model requires selling private preferences. Payment should never bypass the relevance rule or change an organic result without an explicit explanation.

| Priority and model | Who pays, for what | Fit and trust tradeoff | Low-cost validation experiment |
| --- | --- | --- | --- |
| 1. Optional resident/household membership | A resident pays for a useful saved shortlist, a longer planning window, and chosen reminders; keep basic tomorrow discovery available without payment. | Recurring planning fits the current saved profile. Thin inventory would make a subscription hard to justify, and these proposed extras do not exist yet. Don't paywall factual accuracy, privacy, unsubscribe, or preference editing. | After repeat use, show an honest concept for **€3/month**, explicitly an experimental price rather than a market benchmark. Ask whether the participant wants a follow-up invitation at that price. No checkout or charge for an unavailable product. A later paid pilot would be needed to establish willingness to pay. |
| 2. One labeled sponsor placement | A venue or organizer pays for a clearly identified placement in an edition with suitable public event context. | Could fund free access, but creates pressure to favor paying venues. Keep it separate from the organic ranking, apply the same suitability checks, and give users control over sponsored content. Sponsors receive no subscriber profiles or individual activity reports. | Test a static edition with one plainly labeled “Sponsored” card. Check whether readers can identify it and still trust the shortlist. With separately arranged voluntary interviews, ask potential sponsors whether they would pay for that disclosed format before building sales tooling. |
| 3. Disclosed booking referral | An organizer or ticket seller pays when a user books through an agreed referral link. | Payment can follow a useful action, but availability of referral arrangements is unverified. Commissions can bias coverage toward paid events, and external booking sites may track visits. Preserve free-event selection and disclose the commercial link beside the action. Share no profile or email with the seller. | Test whether an ordinary organizer link already attracts consideration. Then check whether a willing organizer can support a transparent referral arrangement. Treat clicks as interest, not bookings or attendance; do not invent an affiliate offer. |
| 4. A public local-agenda service for hosts | A hotel, coworking space, or employer pays for a maintained public agenda or reusable edition for guests/members. | Public event information can serve multiple readers without sharing subscriber data. Buyer needs may pull Brisa toward manual curation, custom branding, and support rather than the resident product. | Show a static public edition to a few voluntary prospective buyers and ask for a concrete trial request, including the update frequency and support they expect. Do not build a portal until someone commits to testing that limited service. |

Choose the membership hypothesis first, after testing usefulness. It connects payment to the person's benefit and avoids introducing advertiser incentives during an already small relevance test. A price-interest response is a reason to test a paid service, not proof of revenue.

**One two-week experiment**

Use guided previews and a small static prototype for the shortlist, empty states, and brief explanations. Leave the other proposals out of this experiment. Invite 8–12 consenting València residents who regularly choose activities with school-age children, since the current profile already supports that context. This is a deliberately narrow cohort, not a claim that families are the largest market. Recruitment and participant contact are proposed future work; this review did neither.

1. **Days 1–2: define and inspect.** Prepare normal, empty, all-filtered, and uncertain preview examples. Ask five participants to explain each result and choose a next action. Establish three or more days when each pilot participant actually wants a plan. Inspect the available source inventory and check event dates before showing it.
2. **Days 3–9: observe real use.** Use dated listings from the real preview path on those chosen days. Ask one question: “Is there anything here you'd seriously consider?” Let people open the organizer page or save/copy an event. Review a small sample of exclusions for obvious false rejections. Keep this browser-based while delivery remains disabled; any later email study needs its own explicit opt-in and completed delivery readiness checks.
3. **Days 10–12: test the presentation.** Show the compact shortlist and explanation prototype using the same event evidence. Repeat the empty-state comprehension task and ask whether tomorrow or a longer window fits participants' actual plans. Record failures and corrections, rather than rebuilding onboarding or adding new categories during the study.
4. **Days 13–14: decide.** Ask returning participants about the €3/month membership concept and an optional follow-up invitation. Publish the counts with denominators and the source limitations. Make one decision: improve coverage, adjust the planning window, or test a limited paid service.

Proposed decision rules below are study rules, not industry benchmarks:

| Question | Continue criterion | Stop or change direction |
| --- | --- | --- |
| Can people understand the result? | At least 4 of 5 distinguish an empty search from rejected candidates and understand that eligibility alone is not a final recommendation. | If not, revise the copy and result layout before adding features. |
| Is the inventory useful? | At least 70% of chosen-day previews contain one event the participant would seriously consider. | Below 50%, pause growth and paid-feature work to address coverage. Between 50% and 69%, investigate the missing days/types before expanding the pilot. |
| Does usefulness recur? | At least half of active participants take a planning action on two separate chosen days. | If fewer do, investigate the date window or practical detail gaps. A single click or completed signup is insufficient. |
| Is membership worth another test? | At least 3 returning participants request a follow-up at the stated experimental price, with at least 8 active participants in the study. | Lower interest leaves the membership hypothesis unsupported. Fewer than 8 active participants means insufficient evidence, not a market verdict. Never report stated interest as paid conversion. |

An organizer click, save, or copy indicates consideration, not attendance. Any materially wrong date or invented practical fact in the sample needs correction before that card returns to the test. Clear false exclusions need investigation rather than reassurance based on a model score. If most participants need a week to plan, that evidence argues against a tomorrow-only membership even when they like the design.

Keep measurement small: a random study code, nominated day, result state, consideration yes/no, and action category. Collect structured feedback voluntarily, keep contact details separate, and delete the study-to-contact mapping after 30 days. Avoid raw preference exports, email-open tracking, and cross-site tracking. Continue the existing provider boundary: only the fields required for ranking leave the application; email, identity, and session data stay out of prompts. Sponsors and referral partners get no private profile data.
